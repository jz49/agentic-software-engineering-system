# ADR-001: Slugs are base62 of a database sequence value, stored as a column

## Status

Accepted — 2026-09-23. The *choice* of base62-of-primary-key was made by the human at the requirements gate; this ADR records the alternatives that were weighed there, and decides the two consequential sub-questions the gate left open: **where the id comes from**, and **whether the slug is stored or derived**.

## Context

A short link needs an identifier that is short, URL-safe, and unique. Uniqueness must hold under concurrent creates, and the service must not be able to hand the same slug to two different targets — that failure mode is link hijacking, and it is silent.

Two families of answer exist. Derive the slug from something monotonic and unique that the database already gives you, or generate it randomly and handle collisions. The requirements gate chose the first and accepted its named cost: sequential slugs are enumerable, so a short link can never be treated as a secret.

That leaves two questions the gate did not answer, both of which change the write path:

- The id can come from an `IDENTITY` column (known only *after* the insert) or from a sequence drawn *before* it. The first forces two writes per link.
- The slug can be stored in a column, or computed from the id on every read. If it is derived, the encoding function becomes part of the persisted data's meaning.

## Decision

`link_id_seq` is an explicit PostgreSQL sequence. The application draws `nextval` **before** building the row, encodes it with `SlugCodec.encode(long)` into base62 over the alphabet `0-9A-Za-z`, and writes `(id, slug, target_url, created_at)` in a single `INSERT`.

The slug is **stored** in `link.slug` with a unique index, and the redirect path resolves it with `findBySlug` — not by decoding the slug back to an id. `SlugCodec.decode` exists for diagnostics and is not called on the read path.

`SlugCodec` is pure and static: no Spring, no I/O, no knowledge that ids come from a database. It is table-tested.

Sequence starts at 100000, so the first slug is three characters (`Q0u`) rather than `1`.

## Alternatives considered

**Random slug with a collision-retry loop** (e.g. 7 random base62 characters, insert, catch the unique violation, retry). This is what most public shorteners do, and it buys the property this design cannot have: slugs are unguessable, so enumeration is infeasible. Rejected at the requirements gate. The cost it carries is real: a write path whose latency has a tail determined by the birthday problem, a retry loop that must be bounded and whose bound is a tuning parameter nobody can derive from first principles, and a test surface that has to simulate collisions to exercise its own error path. Collision-free-by-construction means there is no retry loop to get wrong, and that is worth a great deal in a system this small. The cost accepted in exchange is enumerability, which is recorded as an accepted risk in the understanding and which forecloses ever treating a short link as a capability.

**`GENERATED BY DEFAULT AS IDENTITY` with `GenerationType.IDENTITY`.** The obvious default, and it is what most Spring tutorials show. Rejected because the id is not known until the insert returns, so the slug cannot be part of the insert. The row must be written, the generated key read back, the slug computed, and the row updated — two writes on the only write path the service has, and a window in which a row exists with no slug (or a nullable slug column, which then cannot carry `NOT NULL` and weakens the schema permanently). Drawing from a sequence costs one extra round trip for `nextval` and yields one `INSERT` with every column final. A sequence can also be pooled later if throughput ever justifies it — drawing a block of values per round trip — whereas an identity column cannot be batched at all.

**UUIDv4 or ULID as the slug.** Unguessable, collision-free without coordination, and generatable entirely in the application with no database round trip. Rejected because the output is 22–36 characters. A 26-character "short" link is not a short link, and the whole product is the shortening. Hashids or a similar obfuscating encoder over the sequence value was the near-miss variant — it keeps the length and hides the ordering — but it makes slugs depend on a secret salt, which is then a secret that must be managed, rotated never, and backed up or every link in the system breaks. For an explicitly anonymous service with public links, buying obscurity at the price of a load-bearing secret is a bad trade.

**Hash the target URL (e.g. first 7 characters of SHA-256) as the slug.** Gives free deduplication: the same URL always yields the same slug. Rejected on two counts. Truncated hashes collide, so it reintroduces exactly the retry loop that base62-of-sequence was chosen to avoid, but now with collisions between *different* URLs, which is the hijacking failure. And it makes deduplication mandatory rather than optional, contradicting assumption 7 in the understanding, which explicitly allows one URL to have several slugs.

**Derive the slug at read time instead of storing it** (`decode(slug) -> id -> findById`, no `slug` column, no unique index). Genuinely attractive: it removes a column, removes an index, removes a write-time cost, and turns the redirect into a primary-key lookup. It was rejected for one reason that outweighs all of that — it makes the encoding function part of the persisted data's meaning. Change the alphabet, change the padding, fix a sign-handling bug in `decode`, and every link ever issued silently resolves to the wrong target or to nothing. There is no migration for it, because there is no data to migrate; the data is a function. Storing the slug means the encoder can be changed, or replaced entirely by custom aliases, and every existing link keeps working because the mapping is written down rather than recomputed. A column and an index is a very cheap insurance premium against a class of bug with no recovery path.

**Start the sequence at 1.** Rejected for cosmetics that are not only cosmetics: one-character slugs look like a defect, they consume the shortest and most collision-prone part of the path namespace, and `/1` is indistinguishable from a broken link when someone reports it. Starting at 100000 costs nothing — base62 does not reach 11 characters until roughly 2^63.

## Consequences

**Made easy.** No *collision* retry loop, so no bounded-attempt tuning and no collision test fixtures. One `INSERT` per link. Slug uniqueness is enforced by the database *and* true by construction, so the unique index should never fire — and if it does, an invariant has broken and the 500 is correct. `SlugCodec` is pure, so the encoding is table-tested in milliseconds with no Spring context, which is where most of the behavioural confidence in this feature lives.

**Made hard.** Every link is enumerable. `/Q0u`, `/Q0v`, `/Q0w` walks the entire corpus, and the slug also leaks creation order and approximate volume — a competitor can count links created between two timestamps by shortening two of their own. This is accepted, it is written in the understanding, and it must be re-examined the moment anyone proposes shortening something non-public.

**Foreclosed.** A short link can never be a secret or a capability. Any feature that would rely on unguessability — private links, one-time links, unlisted sharing — requires changing slug generation, and because slugs are stored rather than derived, that change can be made for *new* links without breaking old ones. That is the escape hatch the store-the-slug decision buys, and it is the reason the decision was made.

**The traps to watch.** `Link.id` carries **no `@GeneratedValue`** — the application draws `nextval` itself through `LinkRepository.nextId()`, because the reserved-slug retry (ADR-007) must be able to request a second value after inspecting the slug the first one produced, which a Hibernate-managed generator cannot do. `design.md` §5.1 states the mechanism in full. Two consequences:

- With no `@SequenceGenerator` there is no `allocationSize`, and so none of the classic Hibernate defect in which an entity declaring `allocationSize` 50 against a database `INCREMENT BY 1` hands out ids the database later reissues — a failure that appears as duplicate keys long after deployment, under load, with no obvious cause. If a `@GeneratedValue` is ever added to this entity that trap returns, and the two numbers must then change together. `schema.sql` carries the warning at the sequence definition.
- Because the id is assigned by hand, **`Link` must implement `Persistable<Long>`** so that `isNew()` is true on a fresh instance. Otherwise Spring Data's `save()` sees a non-null id, treats the entity as detached, and calls `merge()` — issuing a `SELECT` before the `INSERT`, quietly converting the one-write claim above into two. This is the most likely way this decision gets implemented wrong, and it is invisible unless someone reads the SQL log.
